## 1. 学习目标：每个工具你最终要会什么

初学者最容易犯的错是「什么都学一点，什么都不会用」。所以先定死每个工具的**验收动作**——能做到这件事，就算掌握。

| 工具 | 学完你能做到（可验证的动作） | 在项目里靠什么练 |
| --- | --- | --- |
| **Codex** | 能把一个大需求拆成小任务，写出结构清晰的提示词，并且**看得懂、能审查**它生成的代码 | 每个里程碑都走「先讲思路 → 再写代码 → 再写测试 → 再 review」四步 |
| **Git** | 会 init / status / add / commit / log / diff / branch / checkout / merge，能看懂冲突并解决 | 每个功能一个分支，一天至少 3 次小提交 |
| **GitHub** | 会建仓库、push、开 Issue、发 Pull Request、写 README、用 PR 做代码审查 | 每个里程碑 = 1 个 Issue + 1 个 PR |
| **Python** | 语法、函数、类、模块、虚拟环境、文件读写、pytest 写测试 | 阶段一用 Python 写命令行版贪吃蛇；阶段三写分析脚本 |
| **Node.js** | 理解 npm、package.json、模块、异步/回调、用 Express 起服务、写 REST 接口 | 阶段二、三用 Node.js 做网页版游戏和排行榜后端 |

> 关键心态：**这个项目的代码量不重要，流程的完整度才重要。** 一个功能完整的小项目，按正确流程走一遍，胜过五个半途而废的大项目。

## 2. 为什么选「贪吃蛇」

不是因为它简单，而是因为它**正好能逼你把五种工具都用上**：

1. **逻辑清晰但完整**：移动、碰撞、吃食物、计分、结束判定——麻雀虽小五脏俱全，能覆盖变量、循环、条件、函数、数据结构。
2. **两种语言天生都有活干**：Python 写命令行原型（练基础语法），Node.js 写网页版后端（练服务端），不是硬凑。
3. **天然需要前端 + 后端**：排行榜功能一加，就必须要服务器、要接口、要数据库——这是真实项目的形状。
4. **可测试**：游戏逻辑是纯函数，非常适合练 pytest 和 Node 的单元测试。
5. **可扩展性极强**：做完基础版，你可以加 AI 自动玩、加音效、加主题皮肤、加多人对战——永远有下一步。

## 3. 游戏设计

### 3.1 核心玩法

- 蛇在网格上持续前进，玩家用方向键控制上下左右。
- 吃到食物：蛇身 +1，分数 +10。
- 撞墙或撞到自己：游戏结束。
- 分数写入排行榜，显示前十名。

### 3.2 完整状态机（先想清楚，再写代码）

```
READY  --按空格-->  RUNNING  --按 P-->  PAUSED
  ^                   |  ^                 |
  |                   |  +-----按 P--------+
  |                   v
  +---------------- GAME_OVER  --按 R---> READY
```

**为什么先画这个？** 因为这是你第一次练习「用 Codex 讨论设计而不是要代码」。状态机想清楚了，后面所有代码都是填空。

### 3.3 数据设计

```
蛇身    = 坐标队列（头在队首），每步：头部入队，没吃到食物就尾部出队
食物    = 一个随机坐标，必须落在空白格
方向    = 当前方向 + 下一步方向（分开存，防止一帧内连按两下反向自杀）
分数    = 吃到食物次数 × 10
```

最后一条是经典坑：如果只存一个方向变量，玩家快速按「右→下」会被识别成反向撞死自己。这个坑值得你亲手踩一次。

### 3.4 界面

| 版本 | 界面 | 阶段 |
| --- | --- | --- |
| 命令行版 | 终端里用字符画格子（`@` 是蛇，`*` 是食物） | 阶段一 |
| 网页版 | Canvas 画布，20×20 网格，带分数板和开始/暂停按钮 | 阶段二 |

├── python-prototype/      # ── 阶段一：Python 命令行版
│   ├── main.py
│   ├── game.py            # 纯逻辑，方便测试
│   ├── requirements.txt

├── web/                   # ── 阶段二：网页版
│   ├── public/
│   │   ├── index.html

## 5. 里程碑计划

### M0 · 环境与工具链打通（预计 2–3 小时）

**目标**：五样工具全都能跑起来，并且互相连接。

**要做的事**

1. 注册 GitHub 账号，配置 SSH key 或 Personal Access Token。
2. 在本地建仓库：`git init`，配置 `user.name` / `user.email`。
3. 在 GitHub 上建 `snake-lab` 仓库（**不要**勾选自动生成 README，这样你能亲手走一次 push）。
4. 让 Codex 帮你写第一版 `README.md` 和 `.gitignore`。
5. 完成第一次 `git add` → `commit` → `push`。

**新学的 Git 命令**：`init` `config` `status` `add` `commit` `log --oneline` `remote add` `push -u`

**完成标准**
- [ ] GitHub 上能看到 README 正常渲染
- [ ] 本地 `git log` 能看到你自己的提交记录
- [ ] 你能不看笔记说出 `git status` 和 `git diff` 的区别

> 💡 **给 Codex 的提示词示例**
> 「我是 Git 初学者。请告诉我从零把本地文件夹推到 GitHub 的完整命令序列，每一步用一句话解释这条命令在做什么、失败时最常见的原因是什么。不要用 `git commit -am` 这种一步到位的写法，我想看清楚每一步。」

---

### M1 · Python 命令行版贪吃蛇（预计 8–10 小时）

**目标**：游戏逻辑跑通，并且有测试。这是你第一次写真正的程序。

**要做的事**
1. 建 Python 虚拟环境，学会 `venv` 为什么存在。
2. **先让 Codex 讲思路**：让它描述贪吃蛇的循环该怎么写，但不给代码。
3. 自己动手写出 `game.py` 的骨架（`Snake` 类、`move()`、`eat()`、`is_dead()`），卡住了再问 Codex。
4. 用 `main.py` 加终端渲染和键盘输入。
5. 用 pytest 给纯逻辑写 5–8 个测试（比如「蛇撞墙返回死亡」「吃到食物长度 +1」）。
6. 故意改坏一行代码，看测试是怎么报警的。

**新学的 Python**：虚拟环境、类与对象、`list` / `deque`、字典、模块导入、`random`、异常处理、pytest
**新学的 Git**：开分支 `feature/python-prototype`、合并回 main、`git diff` 检查改动

**完成标准**
- [ ] `python main.py` 能玩，吃到食物变长，撞墙结束
- [ ] `pytest` 全绿，至少 5 个测试用例
- [ ] 你能给 Codex 解释每行代码在做什么（讲不出来说明没懂，回去问 Codex）
- [ ] 至少 8 次有意义的提交，每次提交信息能看懂

> ⚠️ **本阶段最大陷阱**：直接说「帮我写一个贪吃蛇」。你会得到一个能跑但你看不懂的程序，学习效果为零。
> 正确问法：「我想用 Python 写贪吃蛇，请先只讲设计思路和数据结构，不要写代码。我理解后再逐步给我代码。」

---

### M2 · Node.js 网页版（预计 8–10 小时）

**目标**：把游戏搬到浏览器，学会 npm 和 Express。

**要做的事**
1. `npm init`，理解 `package.json` 是什么，为什么 `node_modules` 不能提交。
2. 用 Express 起一个静态服务器（`express.static`）。
3. 把 Python 版的逻辑**翻译**成 JavaScript（这是最有价值的一步：同一个逻辑两种语言实现对比）。
4. 用 Canvas 画出来：`requestAnimationFrame` 游戏循环、键盘事件监听。
5. 加分数板、开始/暂停按钮、游戏结束弹窗。

**新学的 Node.js**：npm 与依赖管理、CommonJS / ESM 模块、`require` 与 `import`、异步与事件循环、Express 路由、静态资源
**新学的 Git**：`feature/web-version` 分支、用 `git log --graph` 看分支历史

**完成标准**
- [ ] 浏览器打开 `localhost:3000` 能玩，画面流畅不卡顿
- [ ] 你能说清楚「前端代码」和「后端代码」分别运行在哪里
- [ ] `git log --graph --oneline` 能看到至少三条分支线合并的痕迹

> 💡 **对比学习法**：把 Python 的 `move()` 和 JS 的 `move()` 并排放在一起看，让 Codex 解释两种语言的差异（列表 vs 数组、缩进 vs 花括号、类型系统）。这是理解「语言只是工具」最快的方式。

---

### M3 · GitHub 流程 + 排行榜后端（预计 8–10 小时）

**目标**：开始像真正的开发者一样协作——哪怕团队只有你和 Codex。

**要做的事**
1. 在 GitHub 上给你的任务开一个 Issue，写清楚需求。
2. 从 Issue 建分支，写代码，提交，开 Pull Request。
3. 让 Codex 对你的 PR 做一次 code review，把它的意见当成同事的评论来回应。
4. 后端实现 REST 接口：
   - `POST /api/scores` 提交分数
   - `GET /api/scores/top` 查排行榜
5. 用 SQLite 存储分数（先存文件里也行，重点是理解「数据持久化」）。
6. 前端接上接口，玩完一局能提交成绩、看到排行榜。

**新学的 Git / GitHub**：Issue、Pull Request、代码审查、冲突解决（**故意制造一次冲突**再解决它）
**新学的 Node.js**：REST API 设计、HTTP 方法、JSON 请求响应、数据库读写、错误处理

**完成标准**
- [ ] 至少 3 个已合并的 PR，每个都有清楚的描述
- [ ] 排行榜能持久化：重启服务器后分数还在
- [ ] 你至少解决过一次真实的 merge 冲突
- [ ] 提交历史是「一件事一个提交」，而不是「update」「修一下」这种无意义信息

> 💡 **冲突练习方法**：在两个分支上修改同一行，然后合并。第一次看到 `<<<<<<< HEAD` 会懵，但这是必须过的一关。让 Codex 解释冲突标记的含义，你自己动手解决，别让它代劳。

---

### M4 · Python 工具链 + 打磨发布（预计 6–8 小时）

**目标**：让项目从「能跑」变成「拿得出手」，并完成闭环。

**要做的事**
1. `tools/stats.py`：读取分数数据库，算出最高分、平均分、游戏局数、每日趋势（练 Python 数据处理）。
2. `tools/auto_player.py`：写一个贪心算法自动玩贪吃蛇，把 AI 分数提交进排行榜（会非常有意思）。
3. 补文档：README 加上截图、玩法学、如何本地运行。
4. 打第一个正式版本标签：`git tag v1.0.0`。
5. （可选）部署上线，让朋友也能玩到。
6. 写一份 `RETROSPECTIVE.md`：这个项目里你学会了什么、哪里卡最久、下次怎么改进。

**完成标准**
- [ ] `python tools/stats.py` 能输出一份漂亮的统计报告
- [ ] AI 自动玩家能稳定得分（哪怕分数不高）
- [ ] 一个完全不认识你的人，只看 README 就能在本地把项目跑起来
- [ ] 仓库里有 `v1.0.0` 标签
- [ ] 你写完了一份复盘文档

## 6. 每日 / 每次写代码的标准流程

把这张流程贴在显示器旁边。**每次坐下来写代码，都按这个顺序走**：

```
1. git pull                      ← 开始前先同步，好习惯
2. git checkout -b feature/xxx   ← 开一个针对本次任务的分支
3. 跟 Codex 讨论方案              ← 先讲思路，后要代码
4. 写代码 + 立刻运行验证          ← 小步，不要一次写 200 行
5. git diff                      ← 提交前一定看一眼改了什么
6. git add <具体文件> + commit    ← 小步提交，信息写清楚做了什么
7. 卡住了？先自己试 15 分钟，再问 Codex
8. 阶段完成 → push → 开 PR → 让 Codex review → 合并
```

**这条流程本身比任何代码都重要。** 你以后做的所有项目都会用到它。

## 7. Codex 使用手册（初学者最容易用错的地方）

### 7.1 三种模式，按场景切换

| 模式 | 什么时候用 | 提示词长什么样 |
| --- | --- | --- |
| 🎓 **讲解模式** | 遇到不懂的概念 | 「用初学者能懂的话解释什么是虚拟环境，举一个具体例子，不要给代码」 |
| 🤝 **结对模式** | 要写新功能 | 「我要给贪吃蛇加暂停功能。先告诉我需要改哪几个文件、每个文件改什么逻辑，我确认后你再写代码」 |
| 🔍 **审查模式** | 代码写完想检查 | 「审查我这段代码，指出 3 个最可能出问题的地方，按严重程度排序，先别改」 |

### 7.2 好提示词的公式

```
背景（我在做什么、我是什么水平）
+ 目标（我想要什么结果）
+ 约束（用什么技术、什么风格、不要什么）
+ 验收（怎么算成功）
```

**对比一下**

❌ 差：「帮我写贪吃蛇」

✅ 好：
> 我在用 Python 3.14 学编程，正在写命令行版贪吃蛇，水平是刚学完函数和类。
> 我写好了 `Snake` 类和 `move()` 方法，但吃到食物后蛇身没有变长。
> 我的思路是「吃到食物时不要删掉尾巴」，但不确定怎么判断。
> 请先指出我的思路哪里有问题，不要直接给完整代码。如果我的思路是对的，告诉我该在 `move()` 的哪一步加判断。

### 7.3 三条铁律

1. **看不懂的代码不许提交。** 让 Codex 逐行解释，或者让它换成更简单的写法。这是 vibe coding 学习法唯一不能省的一步。
2. **不要让它一次生成整个项目。** 一次给一个函数、一个功能。你参与度越高，学得越多。
3. **每次它改完代码，都要自己运行一次。** Codex 会说「完成了」，但只有运行结果算数。

### 7.4 危险信号（出现这些说明用法跑偏了）

- 🚩 你连续三次直接复制粘贴它的输出，没有读代码
- 🚩 你的提交信息全是「更新」「修改」，说不清那次改了什么
- 🚩 程序报错你的第一反应是「把错误贴给 Codex」，而不是先自己读错误信息
- 🚩 你说不出 `game.py` 里任意一个函数的作用

**遇到这些情况怎么办？** 停下来，回到「讲解模式」，让它把当前这段代码给你讲一遍。

## 8. Git / GitHub 规范（简单版，够用就好）

### 分支命名

```
main                     ← 永远可运行的代码
feature/web-version      ← 新功能
fix/snake-eat-bug        ← 修 bug
docs/update-readme       ← 只改文档
```

### 提交信息格式

```
<类型>: <一句话说明做了什么>

feat: 添加贪吃蛇吃到食物变长逻辑
fix: 修复快速连续按键导致反向自杀的 bug
test: 为碰撞检测添加单元测试
docs: README 补充本地运行步骤
chore: 添加 .gitignore 忽略 node_modules
```

好提交信息的标准：**三个月后你自己看到它，能想起当时改了什么。**

### `.gitignore` 必须包含

```gitignore
# Node
node_modules/
npm-debug.log*
.env

# Python
__pycache__/
*.pyc
venv/
.venv/

# 数据库与编辑器
*.sqlite
*.db
.vscode/
.DS_Store
```

### Pull Request 描述模板

```markdown
## 做了什么
给游戏加了分数排行榜，玩完一局可以提交成绩。

## 怎么验证
1. npm start
2. 玩一局让蛇撞墙
3. 在弹窗里输入名字点提交
4. 刷新页面，分数应出现在排行榜中

## 遗留问题
排行榜还没做分页，超过 100 条会卡。
```

### 初学者常见的四个事故

1. **把 `node_modules` 提交了** → 仓库瞬间几万文件。发现后立刻 `git rm -r --cached node_modules`。
2. **把密钥写进代码** → API key、密码绝不能进仓库。用 `.env` 文件 + `.gitignore`。
3. **只提交到 main** → 分支策略的意义在于「随时能退回可用状态」。
4. **一个提交塞十个功能** → 出问题时 `git revert` 会退掉所有东西，无从下手。

## 11. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| **「复制粘贴式学习」** | 代码能跑但你说不出原理 | 每段代码提交前，让 Codex 逐行讲一遍；讲不出就重写 |
| **环境配置卡住** | pip / npm 报错看不懂，半天没进展 | 把完整报错和你的操作系统贴给 Codex，让它只针对你的环境回答 |
| **贪多求全** | 想一次加上音效、皮肤、多人对战 | 严格按里程碑走，新想法记到 `IDEAS.md`，做完 M4 再回来看 |
| **Git 恐惧症** | 怕搞坏代码，不敢开分支 | 记住：只要你 commit 过，代码永远找得回来。放心大胆试 |
| **中途失去动力** | 第 3 周觉得没意思了 | 看 M4 的 AI 自动玩家——程序自己玩游戏并被排行榜记录，那一刻非常爽 |
| **AI 依赖症** | 遇到问题第一反应是问 Codex | 强制自己先试 15 分钟，写下你的猜测，再去问 |

## 13. 每阶段自测题

能顺畅答出来，才进入下一阶段。

**M0 之后**
- `git add` 和 `git commit` 分别在做什么？为什么是两步？
- 本地仓库和 GitHub 上的仓库是什么关系？

**M1 之后**
- 为什么 `game.py` 和 `main.py` 要拆成两个文件？
- 虚拟环境解决的是什么问题？
- 你的测试用例里，哪个最能体现「游戏规则」？

**M2 之后**
- `npm install` 装的东西放在哪？为什么不能提交？
- 前端代码和后端代码分别运行在哪台机器上？
- 游戏循环为什么要用 `requestAnimationFrame` 而不是 `setInterval`？

**M3 之后**
- 为什么提交分数要用 POST 而不是 GET？
- 什么是 merge 冲突？它为什么会出现？
- 用自己的话说清楚：Issue 和 PR 各自解决什么问题？

**M4 之后**
- 如果有人克隆了你的仓库，他需要几步才能玩到游戏？
- 这个项目里，你最想重构哪个部分？为什么？
